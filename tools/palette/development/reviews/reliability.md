# Clipboard reliability review

Baseline source review, September 6, 2026. Reviewed macOS host, contracts, bridge, service, encrypted store and policy against `development/GOAL.md`. No automated tests or live app control. Findings below are established from code paths; reproduction steps are proposed manual checks, not claimed runtime results.

1. **P1 — Capture/restore loses native formats.** `PaletteHost.swift:350–364` takes only the first URL or plain string; it neither restricts NSURL reads to file URLs nor captures images, multiple files, RTF or HTML. `service.ts:119–123` restores every kind using `item.content`; `node-daemon.ts:61–71` uses pbcopy. A file becomes path text, rich text loses formatting, and image-only copies disappear. Capture bounded native representations and restore with NSPasteboard items. Manually round-trip a two-file selection, a PNG, a formatted text selection and a web URL into suitable apps.

2. **P1 — Recopying destroys pins and source history; own restores can become new clips.** `encrypted-clipboard-store.ts:32–37` removes a matching kind/content regardless of source and replaces it with a new unpinned item. `PaletteHost.swift:366–367` suppresses matching text regardless of kind/source, before capture succeeds. Own pbcopy writes have no ignore marker or change-count suppression. Copy A from app 1, pin A, copy B, copy A from app 2, then restore A: app-specific history and pins are lost or provenance changes. Deduplicate by source and payload, retain stable item IDs/pins, and distinguish host restores.

3. **P1 — Sensitive native clipboard markers are ignored.** The shared policy supports `sensitive`, but the macOS host never reads password-manager concealed/transient pasteboard types or sends that flag. Plain secret strings that do not match the narrow credential regex are retained. Frontmost-app attribution occurs up to 750 ms after copying, so switching apps immediately can also bypass an exclusion and mislabel source. Check sensitive markers before reading payloads, honor the pasteboard's source metadata when trustworthy, and describe attribution limits honestly. Manually check synthetic concealed data and copying from an excluded app while immediately switching away.

4. **P1 — Keychain failure can silently replace unreadable history.** `clipboardStorageKey()` returns a newly generated key without checking `SecItemAdd` success; a locked/unavailable Keychain or duplicate-item result can produce a key that never persists. `EncryptedJsonClipboardStore.load()` swallows every read/decryption/parse failure into empty history; the next capture overwrites the original ciphertext. Treat missing files separately, surface decryption/storage errors, and refuse capture until a stable key is available. Do not silently fallback or reset a damaged store.

5. **P2 — Retention and capacity do not take effect on restart or policy change.** `PolicyClipboardHistory` prunes only after accepted capture. `list()` and `setPolicy()` do not prune: expired history remains visible indefinitely while capture is paused, and shrinking capacity has no immediate effect. Policy changes update in-memory state before settings persistence succeeds (`node-daemon.ts:124–128`). Apply validated policy consistently, prune in a bounded batch on startup/change/read as appropriate, and avoid claiming persisted settings if save fails.

6. **P2 — Failures can leave memory and disk disagreeing.** Store add/pin mutate the cached array/item before the atomic save succeeds. A write failure returns an error but later reads show an unpersisted change; native capture ignores all service errors and suppresses retries via `lastCapturedClipboard`. Build a new state and commit it only after a successful write, and surface capture/storage failures without logging clipboard content.

7. **P2 — Unbounded payload and repeated whole-store work will stall image-heavy use.** There is no per-item byte ceiling or total storage budget. Each change encrypts/serializes the entire history; each expired/overflow removal rewrites it again. List responses send complete item content for every result. Native `NodeServiceProcess.send` writes synchronously on the main thread, so large payloads can block when the pipe fills. Add explicit payload/history budgets, batch pruning, metadata-only list responses and on-demand previews, and move large serialization/pipe work off the main actor.

8. **P2 — Pin/delete/native paste lack a service path.** The store has pin/remove primitives, but contracts and bridge expose neither; there is no return-to-app paste operation. Add end-to-end operations with honest false/error handling for deleted items, missing files, unavailable destination apps and Accessibility permission. Review restored formats before posting paste, preserving a working copy-only path.

Final approval is withheld pending implementation and fresh manual runtime evidence. Follow-up should verify source/pin stability, all four formats, restart, privacy controls, storage failures, and realistic larger/image-heavy histories using synthetic content in an isolated profile.

## First implementation follow-up

Source review of the first working-tree implementation (including `ClipboardSupport.swift`), September 6. No runtime claims, automated tests or UI actions. Native supported representations, multi-file capture, explicit paste/copy paths, source-aware dedup with stable pins/IDs, pre-save cache isolation, Keychain add checking, and decryption-error preservation address substantial baseline failures. These remaining issues need action:

1. **P1 — Large history work still blocks the app and scales poorly.** `NodeServiceProcess.send()` still serializes and synchronously writes capture JSON on the main actor; the new 8 MiB raw capture allowance permits more than 10 MiB base64 requests. A busy daemon can fill the pipe and stall the native UI. `PolicyClipboardHistory.prune()` still calls `remove()` for each expired/overflow row, and each removal encrypts and rewrites the complete remaining store. Reducing a 200-item history to 20 therefore produces 180 full writes before the response. Batch prune in one mutation and use ordered asynchronous pipe writes. Manually check a large synthetic image history while reducing retention/capacity and opening/navigating the launcher.

2. **P2 — Oversized or unsupported captures disappear silently.** `ClipboardSupport.capture()` returns nil when combined representations exceed 8 MiB. Apps commonly offer both PNG and TIFF for the same image; their aggregate can exceed that limit even when one usable representation fits. No user-visible skip reason distinguishes this case from empty/sensitive clipboard. Choose a bounded useful representation when possible, and report an actionable oversized-content status without exposing contents. Verify an image offering both formats around the limit.

3. **P2 — Newline-containing filenames cannot be restored.** Capture correctly saves per-item native file URL representations, but `ClipboardSupport.restore()` validates file availability using `content.split(separator: "\n")`. A legal macOS filename containing a newline becomes multiple nonexistent paths and throws before using its intact file URL representation. Derive validation paths from saved `.fileURL` representations (and retain display-content fallback only for old entries). Manually copy/restore a synthetic file with a newline in its filename.

4. **P2 — Review mode must not silently weaken capture privacy.** The newly added `--review --data-dir` branch supplies a fixed publicly known encryption key while starting ordinary clipboard monitoring with the default enabled capture policy. An unrelated copy during a review session can be retained in that review directory with effectively public encryption. Prefer a per-profile random key with restrictive permissions and default review capture paused until explicitly enabled for synthetic checks; at minimum prevent review mode from pointing at the normal profile. This is a review-harness isolation issue, not evidence that ordinary production Keychain encryption is broken.

Other limits remain for final verification: capture source is still inferred from foreground/deactivation timing rather than pasteboard ownership; nil CGEvent creation returns without resolving the request; image decoding/thumb rendering occurs on the main actor; list refresh still transports all content/thumbnails every two seconds. Source inspection alone cannot establish practical retrieval latency, correct direct paste, native application interoperability, or memory stability.

## Second implementation follow-up

Source review of the revised working tree, September 6. No automated tests or UI actions. Confirmed batch `removeMany` pruning, ordered background JSON encoding/pipe writes, avoiding redundant TIFF when PNG exists, thrown oversized-capture errors, file availability checks from native file URLs, a random 0600 review-profile key, and synchronous deactivation capture. These changes address the four previous findings structurally; performance and source attribution still require fresh runtime checks.

- **P2 — Capture failure feedback is transient and normally lost.** `PaletteHost.reportCaptureError()` only dispatches `paletteCaptureError` into the WebView. `ClipboardView` owns the listener and is absent while the launcher view is active; every clipboard reopen remounts that component and clears its feedback state. Launch in the normal launcher view, copy an oversized image in another app, then open history: the failure event had no listener, and the clip is missing without explanation. The same affects background storage failures. Retain the latest capture failure in host/bridge state and show it on the next clipboard open, with an explicit clear/dismiss path.

- **P2 — Compressed-image bytes do not bound decode memory or main-thread latency.** `ClipboardSupport` limits encoded representations to 8 MiB but decodes/renders original images on the main actor with no pixel-dimension ceiling. A highly compressible very large PNG can fit that byte budget while requiring hundreds of MiB or more for decoding; bounding the rendered thumbnail to 900 logical points does not bound decoding of its source. Inspect dimensions before rendering and impose a practical pixel budget or use bounded thumbnail decoding off the main actor. This source-backed risk needs a synthetic large-dimension manual check; no stall/memory figure is claimed here.

The synchronous deactivation callback removes an avoidable source-attribution scheduling delay. It does not prove pasteboard ownership; verify actual copy→immediate app switch and excluded-app flows in the running app. The old nil-CGEvent branch still fails to resolve a paste request; handle that failure if it remains in the final implementation. Approval remains conditional on final source changes and runtime evidence.

## Final source assessment

The host now retains capture errors until dismissal, and the clipboard view requests delivery after installing its listener. ImageIO reads dimensions, rejects images above 40 megapixels or 16,000 pixels per edge, and requests a bounded thumbnail. These changes address the substantive second-follow-up findings. Earlier fixes for native representations, per-source dedup/pin preservation, missing-file validation, encryption failures, batch pruning and background pipe writes remain present. No additional P1/P2 source blocker was identified in this pass.

One small failure path remains: `sendPaste()` returns without resolving its bridge request if either CGEvent allocation fails. Resolve an error and retain copy fallback instead of leaving the operation busy indefinitely. This is established by source, not reproduced runtime behavior.

Source assessment supports the implementation with those explicit limits. ## Larger-history review — checkpoint c2d08668f

Bounded source-only review of supported histories up to 10,000 items and 64 MiB, September 6. No automated tests, benchmark scripts, UI control or measured timing claims. Earlier closure concerned the preceding iteration; this pass specifically examines upper-capacity behavior.

1. **P2 — Overlapping polling can prevent refresh from ever committing.** `ClipboardView.refresh()` increments `refreshVersion` for every request, and the two-second interval launches another request without checking whether the previous refresh is pending. If list responses take longer than two seconds, each completed response has an outdated version and is discarded. The daemon processes requests sequentially, so queued requests and retained payloads can accumulate. Add an in-flight guard (cleared in `finally`) or schedule the next poll only after completion. Preserve mutation invalidation separately so a refresh cannot overwrite a later pin/delete result.

2. **P2 — Unchanged refreshes repeatedly transport and render the entire history.** `node-daemon.ts:listClipboard` excludes representations but returns full text and every 900-pixel thumbnail. Native list enrichment repeats base64 app icons on each row. `ClipboardView` requests the complete unfiltered list every two seconds and renders `visible.map` for every match, potentially 10,000 rows. A text-heavy history can return tens of MiB even without binary representations; every response creates new objects and rerenders/recalculates the whole list. First add a mutation revision/unchanged-list response so idle polling is cheap. Then bound rendered rows with a keyboard-aware visible window, keep small row metadata separate from full preview data, and fetch detailed content only for the selected clip. Content search must continue to search full stored text if previews are truncated.

3. **P2 — Retention calculation remains quadratic despite batched disk writes.** `PolicyClipboardHistory.prune()` computes `remaining` using `items.filter(... expired.some(...))`. When 10,000 items have expired, this performs roughly 50 million ID comparisons before the single removal write. Build a Set of expired IDs or partition eligible/expired items in one pass; then apply the count budget. This is a small direct fix and does not require replacing storage.

4. **P2 — Large response framing and parsing still execute on the main actor.** The ordered writer queue fixes outbound writes, but `consume()` is dispatched to main for every incoming chunk, scans accumulated `buffer.firstIndex(of: newline)` from the beginning, and parses JSON there. For a single large line arriving in many chunks, the already-inspected prefix is scanned repeatedly (quadratic in response length for a fixed chunk size). Retain a scan cursor or move ordered framing and JSON decoding to a dedicated reader queue, returning completed response dictionaries to main. Clear framing state on process termination/restart so a partial old response cannot prefix a new service response.

5. **P2 — Capture cost repeatedly scales with every stored byte.** `EncryptedJsonClipboardStore.add()` recomputes SHA-256 from JSON of each same-app candidate's full representations, then serializes all history to measure capacity, and `save()` serializes all history again before encryption and base64 envelope serialization. At a 64 MiB history, even adding a short text clip repeatedly traverses substantial unchanged payload data and delays the daemon's sequential command responses. Cache each item's fingerprint and serialized byte size in memory when loaded/changed; use those caches for dedup/capacity accounting. A single full encrypted write per mutation remains an explicit cost of the current simple file format; assess that cost with native evidence before considering a larger storage redesign.

Recommended next implementation order: guard polling; make prune linear; prevent unchanged-list retransmission; fix incoming framing/parse ownership; then bound visible rows and cache byte/fingerprint work if representative native checks still show stalls. Verify actual large synthetic histories while typing/searching, copying, pinning and changing retention, and record sizes plus observations. Do not claim upper-limit performance merely because ordinary small histories work.

### Scaling implementation follow-up

Source-only review of the uncommitted scaling changes after c2d08668f. No automated tests or UI actions.

Confirmed the polling in-flight guard avoids periodic overlapping requests; revision responses retain the same cached item array when unchanged; expired-ID Set removes the quadratic retention membership scan; immutable item WeakMaps avoid repeated fingerprint/size serialization; and rows have a fixed 75-pixel CSS height consistent with the virtual window calculation.

`ServiceResponseReader` owns buffer, scan count and JSON decoding on one ordered queue. Its scan count skips only previously inspected bytes; after each newline removal it resets and continues through remaining complete/partial lines. Creating a new reader for each process separates partial framing bytes across restarts. No framing-index correctness problem was found by source inspection. The revision hash covers item IDs/order, capture time and pins, which covers current storage mutation paths: recapture retains ID only for identical source/payload and refreshes time; remove/prune change membership; pins replace the item. WeakMap entries similarly remain valid because current add/pin paths replace stored item objects instead of mutating them.

Two virtual-window correctness issues need coordination with the workflow reviewer:

- **P2 — Active descendant may name an unmounted option.** Manually scrolling away from the selected row removes it from `visible.slice(windowStart, windowEnd)` while the combobox/listbox still expose its ID through `aria-activedescendant`. Keep the selected option mounted at its correct position, or expose an active-descendant ID only while its option is mounted. Preserve the actual selected item for copy/paste.
- **P2 — Background changes can interrupt manual browsing.** The selection scroll effect now depends on the complete `visible` array. A new captured item/revised history changes that array and scrolls back to the selected row, even if the user deliberately scrolled elsewhere without selecting. Restrict forced scrolling to deliberate selection/filter changes or preserve the manual viewport during background updates. An unchanged revision avoids idle jumping, but a real capture still triggers it.

Initial/changed list responses still contain full text/thumbnails, and each mutation still encrypts/writes the complete history once. Those explicit remaining costs are not automatically blockers after these focused improvements; validate representative large native data and report the sizes and observed behavior before claiming upper-capacity performance.

### Scaling source closure

Confirmed the final virtual-window changes: both combobox and listbox expose `aria-activedescendant` only when the selected option is rendered; forced scrolling depends on selected ID and explicit app/search/type filters, not list identity or selected index. A background capture that shifts the existing selection's index therefore does not trigger forced scrolling. Both virtualization findings are closed by source inspection.

The scaling changes are approved from source review, with no further concrete blocker identified in this bounded pass. ## Final storage-failure presentation review

Reviewed the `ClipboardView` history-failure changes read-only. No tests or live UI actions. The latest-request version now owns both loaded data and load errors: stale requests cannot replace the current failure, successful refresh clears it, and failed refresh retains existing cached rows instead of reporting an empty successful load. An initial failed load shows unknown counts and “History unavailable” with the actual error. Polling failures no longer overwrite action/capture feedback. Capture-error dismissal is explicitly distinguished from dismissing unrelated status feedback, so an unrelated message cannot silently clear the host's pending capture error. Settings are disabled until policy is available and while an operation runs. No new concrete reliability regression identified in this bounded source change.

Additional coordinator-reported native checks this cycle:

- A multi-file capture restored both files through Finder; both pasted files were byte-identical to their originals.
- Restoring a missing file was rejected before changing the replacement clipboard marker, confirming preservation of the current clipboard on that failure path.
- In an isolated fixture dated 40 days earlier, an unpinned item expired while a pinned item remained; unpinning the old pinned item then expired it.
- A malformed encrypted envelope retained the same SHA-256 hash while the native app polled its history, supporting the claim that load failure preserves the existing file.
- Same-source recopy verification was inconclusive because other clipboard activity and foreground attribution changed during the check. This is not a deduplication runtime pass; source coverage and previously observed self-restore stability remain distinct evidence.

Source review remains approved for committing this checkpoint, with no additional concrete blocker from these changes. Permission-enabled paste, controlled same-source recopy/exclusion checks and other still-open acceptance work remain explicitly outside that approval. The reviewer did not commit, push, run tests or control the app.
