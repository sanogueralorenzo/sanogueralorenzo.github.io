# Architecture findings

Keep the validated Arch Linux ARM userspace, Android display/audio/input bridges and one Steam session owner. None of the inspected alternatives supplies evidence that replacing this baseline is necessary. Findings below are source observations, not S24 performance results or proof of broader game compatibility.

## Authentication proof gate

Use [JavaSteam 1.8.0](https://github.com/Longi94/JavaSteam/releases/tag/1.8.0) for native Android credential/Steam Guard and CM authentication, rather than implementing RSA/protobuf/CM ourselves. The implemented flow requests SteamClient/client-audience refresh tokens with a Linux identity and verifies native protocol login before Linux handoff. Credential and handoff acceptance still require live account validation. [Steam session documentation](https://github.com/DoctorMcKay/node-steam-session) distinguishes SteamClient tokens from web/mobile tokens; a web sign-in is insufficient proof of a client session. GameNative's reviewed token helper writes Windows Steam files and invokes Wine with tokens in command arguments; it also logs encoded token data. Neither behavior is acceptable to copy. Its account selector file is metadata rather than proof of authenticated client state.

Native Android authentication and Linux-client sign-in are separate steps. GameNative proves the first; its [withheld bootstrap](https://github.com/utkarshdalal/GameNative/blob/231d1365cf1a09b7f1763cfaebd3906628ec1381/THIRD_PARTY_NOTICES) is neither reviewed implementation evidence nor an interchangeable Linux bridge. Before shipping native login, prove that a freshly authorized native SteamClient token establishes our Linux runtime's actual online session and licenses without another login, launches an owned game, and survives client restart. Check token audience/platform requirements. Writing `loginusers.vdf` is insufficient. If handoff fails, report that precise limitation independently from native authentication feasibility and retain Arch. Preserve the existing login and test new material in an isolated private home first. Native passwords/codes must remain transient; persisted tokens require Android Keystore protection and excluded backup. Never print them, encoded forms, request bodies or sensitive exception/subprocess output. A credible login UI and protected runtime handoff must be ready before requesting user account interaction.

## Setup and component ownership

The shared setup installer prepares the existing pinned Arch, matched graphics, Pulse/audio adapters and Valve client. One interruptible lock serializes setup and session preparation. An incomplete setup routes native launch to Setup. Download uses a user-started data-sync foreground service with progress/cancel and timeout/task-removal cleanup; [Android service types](https://developer.android.com/develop/background-work/services/fgs/service-types#data-sync) and [timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout) define its lifetime. Completed installers remain reusable after retry; user home is separate.

Account-dependent tools still need post-login integration. Steam owns its managed depot downloads/verification/update recovery; avoid adding another downloader for the same files. Assembled Arch and Android adaptations remain reproducibly built and versioned, with updates deferred while components are used. Defaults must preserve explicit game overrides. Background preparation and automatic updates will initially be off, and cannot count as complete before enabled/disabled behavior is tested.

## Minimal Arch and updates

Assemble Arch ARM from the explicit seeds and pinned dependency closure in `native/runtime`, rather than pruning an untracked generic filesystem. The validated archive is 162610928 bytes (155.1 MiB); Steam, Proton and graphics remain additional downloads. Retain only dependencies demonstrated necessary, along with licenses, provenance and required resources. Size reductions must include installed size and extraction/update cost, not archive size alone.

Maintainers refresh the package/source locks with `update.py`, review changes, build the image, test on the S24 and publish a versioned checksum-verified archive. Preserve old package inputs for reproducibility. Android installs the tested runtime through staging and recovery while Steam is stopped; home, authentication, games and saves remain separate. Do not run rolling package upgrades inside a trimmed runtime. Steam continues to own its client/depot updates; keep Android adapters separate from replaceable components.

### Protected handoff interface evidence

The production session now owns the protected pipe bridge; shutdown closes it and removes its private files. An initial S24 capability probe passed in 43.361s: an execution shim attached CEF's CDP command/response pipes when `taskset` launched Steam's browser, without replacing verified Steam files. Private mode0600 FIFOs carried a read-only check confirming `SteamClient.Auth.SetLoginToken` and `StartSignInFromCache` exist in the ARM64 client's SharedJSContext. No credentials were used, tokens retrieved, or authentication changed. The integrated runtime and normal session ownership checks passed together in 70.253s; remote/parser error checks passed without exposing synthetic private values. Steam output is drained without persisting arbitrary subprocess content or presenting it in status messages. Processes and test files were cleaned up. The earlier executable-binding attempt timed out before reaching the browser and was removed.

[Millennium pipe setup](https://github.com/SteamClientHomebrew/Millennium/blob/63c3928f0306edd83122c0f5b085a9b1a3d60f55/src/instrumentation/internal/steam_hooks.cc) and [Auth interface types](https://github.com/SteamClientHomebrew/Millennium/blob/63c3928f0306edd83122c0f5b085a9b1a3d60f55/src/typescript/sdk/src/sharedjscontext/globals/steam-client/Auth.ts) supplied investigation references. This is a private client interface, not a documented supported Valve login API. Interface availability does not prove token acceptance, owned-game execution or restart persistence; those remain required live checks.
